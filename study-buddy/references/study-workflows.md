# Study materials and mock review

## Create a document or visual cheat sheet

Start from the requested exam, supplied curriculum and learner's background. Use an official exam blueprint when scope or weights matter and verify its version. For an “all slides” request, inventory the page range, including slides with only images, inspect diagrams, and track which pages contribute to each topic. Group repeated terms and retain slide/page pointers. Identify source gaps or disagreements explicitly.

A cheat sheet should be usable the night before the exam. Open with a labeled architecture or workflow diagram. Use arrows with a specific meaning such as “loads model from,” “sends request,” or “runs on.” Distinguish a sequence of actions from layers in a system. Follow with small comparison tables showing the term, official full name when applicable, job, when to use it, and nearest distractor. Add memory cues and a few cover-and-recall questions with answers on a separate page. Expand acronyms only when supported; label memory aids as mnemonics.

For a longer study guide, organize chapters by objective. Start each with a scenario, illustrate the mechanism, explain the tradeoff and end with an original application question. Use the user's field for examples when known. For an engineer, a deployment or debugging decision often works better than a dictionary definition. A diagram or analogy must preserve the direction of a request and the role of each component. Flag the point where an analogy breaks.

Deliver the requested file in the workspace with an openable link. For PDF or DOCX use available document tools, render and inspect layout, and check diagrams, labels, page references and answer separation. If only Markdown output is feasible, deliver the usable Markdown and state the format limitation. Keep private study material and progress in the session workspace.

## Diagram quality

Choose the drawing based on the question. For "where does it sit?", draw containment boundaries (host, process, storage, external caller), name the running components, and attach a verb and payload to arrows. For "what happens when?", use a sequence with an initiating event, request, processing and response. For a multi-phase system, show deployment separately from steady-state requests. Mark optional paths, scope, and assumptions. See the [worked architecture and sequence](triton-example.md).

Use legible type at the intended reading size, short node labels, consistent direction, generous spacing, and a second cue besides color for meaningful distinctions. Pair a diagram with one concrete scenario and a question the learner can answer by tracing it. For exported documents render the actual diagram to vector or high-resolution art and inspect the final page at reading size for crossed labels, clipped arrows and tiny text. If an arrow implies a false dependency, redraw the boundary or split the views before delivery.

## Explain a concept during practice

Give the plain meaning, its job, and one example. Compare similar terms using a single decision. For instance, an inference server receives a request and returns a prediction; a model repository stores files for the server to load. Draw the two flows independently. For numeric formats use an actual number or range; for tools use a workload. Offer a short mnemonic that the learner can reverse into a correct explanation. A recall check can ask “Which component loads the files?” Leave the exam cursor and score alone during teaching.

## Review a completed mock by voice

Import or read the learner's responses and the matching mock/key. Align by displayed question number and version; count unattempted and ambiguous matches separately. Build review queues for misses, guesses, flags and disputed items. Preserve the original attempt and separately record review outcomes. Start with the requested queue; otherwise prioritize repeated misses within an objective, then lucky guesses. Use saved audio delivery preferences.

For a blind retry, hide the prior choice, key and rationale. Present one exact item and wait. For a debrief, disclose the learner's choice, effective answer, decisive clue and the specific misconception. If the learner wants practice transferring the concept, ask an original variation explicitly labeled as practice and score separately. Close the review with first-attempt counts, retry performance, the most useful distinctions, and source pages to revisit. Avoid ranking small samples as established weaknesses.

For a bank coverage audit, map questions to published objectives with IDs and mark strong, partial and missing coverage. Distinguish practice format and topic alignment from knowledge of live exam content.
